# Design Memory

This file stores long-term design taste, design rules, and reusable lessons for future UI and visual work in this repository.

## Default Design Taste

- Prefer premium, clean, modern, marketplace-ready design.
- Use `.design-brain/APPROVED_TEMPLATE_CORPUS.md` and the local folder `<USER_HOME>/Downloads\Template\Template yang Sudah Masuk Google Drive` as Yusuf's approved-output benchmark for template structure, design-system boards, preview packaging, and marketplace depth. Treat it as taste evidence, not a copyable scaffold.
- A quiet visual mood must never shrink product scope. Template products need the standard structure, sections, states, and page logic expected for their product type.
- When a user asks for a website/template product, build to product completeness first, then make it visually refined. Do not reduce the number of sections just because the design direction is spacious, calm, elegant, or premium.
- When the user gives creative trust, treat it as permission to act decisively: choose a strong product direction, build the complete structure for that product family, and revise visible weaknesses without waiting for frustration.
- For single Figma website/template builds, do not create responsive preview boards or marketplace covers by default. Treat those as opt-in or explicit package-preview surfaces. Redirect that effort into the per-template design system unless the user or delivery contract explicitly asks for responsive previews or cover assets.
- A compact design system board is allowed, but a minimalist receipt board is not. Swatches, typography, one button, and a note are not enough. The board must prove reusable system depth through color-role logic, typography hierarchy, spacing/grid rules, component anatomy, variants/states, reusable section modules, placeholder behavior, surface/effect roles, and source-editing guidance.
- Design system quality is functional coverage, not length or visual busyness. Do not make it long for its own sake, but do not call it complete unless a buyer can understand how to edit, extend, and reuse the template without reverse-engineering the page.
- For multi-template Figma/source work, every template and its own design system board form one atomic pair. Do not start template 2 until template 1 plus design system board 1 are complete, inspected, receipt-backed, and locked. Repeat as `template N + design system N -> audit -> lock -> next template`.
- Quality beats quantity for every template batch. Do not optimize for early completion claims, producing many outputs, or showing completion before the designs have been deeply studied, differentiated, visually inspected, and revised.
- Treat `kaku` as a layout-defect root cause. A template can be polished but still fail if its spatial gesture, zoomed-out section silhouettes, focal path, negative-space shape, module scale variation, or breakout behavior repeats prior templates. Use `.design-brain/LAYOUT_FLUIDITY_EXPANSION.md` before planning or approving similar-feeling layouts.
- Treat local closure similarity as a batch failure, even when the full pages look different. If final proof, CTA, contact, checkout, inquiry, or footer sections share the same visible shape, such as a light form/FAQ/content panel paired with a dark CTA/footer panel, the newer template must be recomposed into a different product-specific action model.
- For batch template work, never present the output until each pair of templates has been audited against each other. If a later template reaches 10 percent similarity against an accepted earlier template, keep the earlier template as the locked fingerprint and rebuild the later template from a fresh structure, motif, rhythm, and product-logic direction.
- For batch template work, treat every page-level scaffold as single-use. After one template is accepted, permanently remove its scaffold from active working context and record a disposal receipt before starting the next template. Keep only primitive helpers and negative pattern locks; never reread, copy, mutate, or data-swap the previous scaffold into the next build.
- Prioritize strong visual hierarchy.
- Use intentional whitespace and spacious layout rhythm.
- Use clean alignment and an obvious grid or layout structure.
- Use a consistent spacing system across sections, cards, controls, and text groups.
- Use polished typography with clear scale, readable body text, and purposeful emphasis.
- Keep CTA focus clear and visually distinct.
- Make the result modern but not generic.
- Avoid generic template-looking UI.
- Avoid clutter and overcrowded sections.
- Avoid inconsistent spacing.
- Avoid random decorative elements, including gradients, blobs, heavy shadows, or ornamental shapes that do not support the concept.
- Avoid childish or overly playful UI unless the user requests that direction.
- Prefer design that feels intentional, polished, and ready for Figma-like or template marketplace presentation.
- The result should feel intentionally art-directed, not auto-generated.
- Treat effects as an art-direction layer, not a decoration checklist. Shadows, glows, blur, overlays, borders, and depth should be considered when they improve hierarchy, premium polish, clarity, or marketplace value.
- If a reference uses effects, study the function behind them and reinterpret the effect system instead of copying values.
- If a reference is premium but visually flat, evaluate whether a subtle original effect system would improve the rebuilt template. Add effects when they help; keep it flat when restraint is stronger.
- For reference-based and batch template work, use the Designer Cognition Layer before structure planning. Learn the human design decision behind attention, emotion, trust, density, proof, conversion, and buyer confidence before deciding sections, cards, CTAs, or visual style.
- For Figma template references, use the professional template reading order before structure planning: product purpose, visual direction, section structure, grid/layout, typography hierarchy, color-role system, image direction, component style, spacing rhythm, visual signature, content logic, responsive behavior, Figma source hygiene, default-template syndrome risks, and original reconstruction. The goal is designer-like system reading, not minimalist fallback or surface copying.
- For website-template work, treat the configured local preview-image corpus, such as `<LOCAL_REFERENCE_CORPUS>/Template Website`, as the evidence source. Classify the product type first, then select matching corpus references so section depth, proof strategy, density, and buyer completeness are evidence-based rather than assumed.
- Treat "standard referensi" as evidence of structure, density, section count, module roles, layout variety, color behavior, effects, gradients, and marketplace completeness. Minimal, clean, or quiet style never means fewer standard roles unless the reference/product type proves a small scope.
- When layout ideas feel exhausted, borrow multiple abstract layout moves from the selected references, then recombine them into a new product-fit structure. Reusing one obvious reference layout is copying; mixing subtle section grammar, composition tension, motif, and module rhythm is premium reconstruction.
- Color systems must be explored as role relationships, not flat palette picking. Ask whether A+B, A+B+C, or a richer A-G role map works for the buyer, contrast, category, CTA hierarchy, and differentiation from other templates.
- For approved-output learning, inspect the accepted template package at three levels: main page, design-system board, and marketplace preview pack. The local approved pattern usually includes a primary design, design system, main cover, colors/typography, features overview, overview-template, Figma file, and support/export material.
- Match structure count to the product type standard. A food restaurant, VR product site, product showcase, creative studio, or music gear store should each receive its own section rhythm, proof logic, commerce/service depth, and design-system scope.

## Operating Rules

- Start with a clear primary user action or visual focal point.
- Before designing a template product, classify the product type and define the expected structure standard. If the standard count or required pages/states are uncertain, research the current market/category before building.
- Before building or critiquing a template product in this workspace, choose 2-4 nearest examples from the approved template corpus when available. Extract buyer friction, section rhythm, proof strategy, visual-language logic, design-system board logic, and preview-packaging logic, then create a new original fingerprint instead of reusing the accepted scaffold.
- For Figma website templates, classify the website product family before section planning. Use landing-page only when landing/campaign/lead-gen intent is explicit; otherwise route to SaaS/product website, corporate/business, service/booking, agency/studio, portfolio/case-study, ecommerce/storefront, marketplace/listing, editorial/blog/CMS, education/course/LMS, docs/help center, dashboard/admin, community/nonprofit, event/travel/hospitality, utility kit, or multipurpose/full website as appropriate.
- Do not carry old task-specific omissions such as "no components", "no devices/mobile/tablet", "no cover/preview", or "desktop/website only" into new briefs as persistent bans. Decide components, responsive/device views, preview/cover surfaces, and desktop scope from the current request, product category, marketplace standard, and buyer value.
- Every designer-cognition claim must be evidence-backed: observed evidence, inferred designer reason, user or buyer effect, business function, reusable thinking logic, originality transformation, and confidence level.
- Reuse abstract thinking logic, not recognizable execution. Trust-before-pricing, calm-to-dense rhythm, evidence-before-action, visual proof, attention flow, and buyer confidence may transfer; exact composition, pacing, component grouping, image placement, visual motif, and CTA staging must be transformed.
- For batch templates, record opening strategy, hero grammar, trust strategy, density rhythm, component system, CTA logic, visual motif, and storytelling arc after each cycle. The next cycle must stay below 10 percent similarity against accepted prior fingerprints.
- For batch templates, also record layout gesture, section silhouettes, composition tension, focal path, negative-space shape, depth layering, module scale variation, and breakout behavior. If two outputs share these axes, rebuild or recompose the newer template before styling.
- For batch templates, record `closureSilhouette` in the structure fingerprint. Compare final-section screenshots locally, not only whole-page screenshots; repair repeated closure grammar with a new action-model silhouette, not recolor, copy, radius, or spacing tweaks.
- For batch templates, record reference-standard evidence before build: observed section count/range, section roles, layout-shape inventory, color-role inventory, effect/gradient inventory, and which reference moves are safe to remix. If those fields are missing, do not claim the output follows the reference standard.
- Before template 2 or later in a batch, confirm the previous scaffold disposal receipt: spent scaffold named, hero grammar/section sequence/module cadence/CTA-proof-footer closure/design-system order discarded, temporary scaffold artifacts deleted or removed from active context, primitive helpers retained, and a blank structure fingerprint prepared.
- Make hierarchy visible through scale, contrast, spacing, placement, and content grouping.
- Use whitespace as structure, not as leftover empty space.
- Keep section rhythm consistent across the page or screen.
- Make alignment obvious; avoid almost-aligned elements.
- Choose typography that improves scanability and confidence.
- Make CTAs easy to find without making the whole screen loud.
- Use color accents purposefully and sparingly.
- Treat responsiveness as part of the design, not a late fix.
- Include accessibility checks for contrast, focus, readable size, and semantic controls when working in code.
- Before final delivery, ask: does this feel like a polished product/template someone would trust or buy?

## Template Image Placeholder Rules

- Source-template image policy is governed by `.design-brain/TEMPLATE_IMAGE_PLACEHOLDER_POLICY.md`.
- If the user asks for a template/source file and does not explicitly ask for generated images, use text clue placeholders for image zones instead of creating final images.
- Reference imagery teaches what kind of replacement slot the buyer needs; it does not require Codex to generate a similar image.
- During any template design process, use images only when they genuinely improve hierarchy, mood, explanation, storytelling, proof, or marketplace value.
- Do not force every template section or slide to include images; let text, spacing, grid, shapes, data, and editorial composition carry the design when that is stronger.
- When a layout needs an editable image area, label the placeholder clearly as `image placeholder: [purpose]` so the buyer/user understands what should be replaced.
- Treat `image placeholder` as a creative placeholder, not a fixed stock-photo requirement; it can represent product shots, screenshots, maps, case-study visuals, textures, brand imagery, or other context-fit visuals.
- Place image placeholder areas intentionally within the composition, with safe cropping, clear boundaries, and enough spacing so the template remains useful after replacement.
- When the template needs a specific human/profile image, such as a doctor, engineer, founder, consultant, teacher, or team member, use `profile photo placeholder: [role]` instead of generating or forcing a fake person image.
- When the template needs data visualization, use a clear marker such as `diagram statistik placeholder`, `chart placeholder`, `timeline diagram placeholder`, `process diagram placeholder`, or another context-fit diagram label instead of forcing a finished diagram.
- Use clue text markers as editable content guidance for the buyer/user; the main design responsibility is to make the structure, spacing, hierarchy, and replacement zones polished and easy to use.
- Keep placeholder clue text short, visible, and purposeful so the user immediately understands what content belongs there without the marker becoming visual clutter.

## Template Icon Cue Rules

- When a studied reference uses icons inside shapes, cards, badges, buttons, feature blocks, or visual markers, reinterpret that need with original editable design icons instead of copying the reference icon style.
- Use icons as functional cues for scanability, category recognition, slide role, feature meaning, or interface affordance; do not add icons as random decoration.
- Keep icons consistent with the template's visual language, stroke weight, corner logic, scale, and container shape.
- Do not label icon areas as image placeholders; reserve `image placeholder` for larger image placeholders such as photos, screenshots, maps, textures, product shots, or case-study visuals.
- If a visual structure would look incomplete without real imagery, add an intentional text clue placeholder so the user understands where to insert a context-fit image.

## Template Effect Judgment Rules

- During reference study, inspect effect language: drop shadows, glow, blur, overlays, glass, gradients, hairline borders, edge highlights, and surface depth.
- Ask what each effect is doing before reusing the idea: separation, CTA focus, premium softness, technical signal, readable imagery, or stronger section transition.
- Reinterpret effects as semantic design-system styles such as `Effect/Soft card shadow`, `Effect/Floating panel`, `Effect/Signal glow`, `Effect/Image overlay`, or `Effect/Hairline depth`.
- Use effects only where they improve the structure: hero panels, product cards, booking forms, dashboard consoles, CTA sections, image placeholders, or quote/testimonial panels.
- A premium flat reference can still inspire a subtle new effect system if it improves polish and editability. A strong flat design can also remain flat when effects would add noise.
- Do not copy effect values, blur intensity, glow color, shadow shape, or exact surface treatment from a reference.
- Screenshot-inspect effects before final delivery. Effects should support hierarchy and depth without creating clutter, muddy contrast, or generic AI polish.

## Learning And Reflection Rules

- Use `REFLECTION_LOG.md` proactively during substantial design work when a reusable process principle becomes clear, even before a visible mistake or revision happens.
- Do not treat reflection only as a post-error or post-revision artifact; use it to preserve useful working rules that can prevent future mistakes.
- When the user explicitly says a process lesson should become part of Design Brain's stable behavior, promote it into `DESIGN_MEMORY.md` without waiting for repeated patterns.
- Keep the boundary clear: reflection captures process lessons, while `DESIGN_MEMORY.md` stores approved stable rules that should guide future design work automatically.
