# Reference Insight System

References are for learning, not cloning.

Reference insight is part of the broader Source-of-Truth Identity Layer. It gives Design Brain a way to grow from references without turning those references into copied layouts.

When the user provides a reference, Codex must extract design insight before designing. A reference can be a screenshot, live site, Figma frame, marketplace preview, template cover, dashboard, landing page, UI kit, branding system, or previous template product.

Codex must not copy the reference layout, section order, composition, component grouping, image placement, spacing rhythm, typography pairing, or visual gimmick. The goal is to understand why the reference works, then reinterpret that logic into a new, original, marketplace-ready template product.

For website-template and Figma website-template work, also load `.design-brain/WEBSITE_REFERENCE_PROMPT_LOCK.md`. The reference is Style DNA and product-standard evidence only. The output must not copy the reference's layout, composition, section order, hero grammar, exact colors, assets, or scaffold.

## Figma Reference Deep Study

When the reference is a Figma link, Figma frame, Figma template file, or `.fig` source, use `.design-brain/FIGMA_REFERENCE_DEEP_STUDY.md` and `.design-brain/FIGMA_PROFESSIONAL_TEMPLATE_LEARNING.md` before structure planning.

Figma references must be studied as source-template systems, not as flat screenshots. Inspect product purpose, visual direction, section structure, grid/layout, typography hierarchy, color-role system, image direction, component style, spacing rhythm, visual signature, content logic, responsive behavior, Figma source hygiene, page/frame scheme, nested groups, component sets, variants, states, design-system panels, auto-layout/source behavior, density rhythm, and product-family standard. Produce a Figma reference schema receipt before building.

Do not use "minimalist", "simple", or a short safe structure as the fallback when the Figma standard is unclear. Classify the product family, inspect more evidence, use category/corpus standards, or ask one targeted question.

## Designer Cognition Gate

Before structure planning, use `.design-brain/DESIGNER_COGNITION_LAYER.md`.

Reference insight must explain human design decisions, not only visible sections. Codex must identify the buyer decision model, designer intent, attention strategy, emotional rhythm, trust strategy, density strategy, conversion logic, component reasoning, repeated designer patterns, non-copy boundary, reusable thinking pattern, and original execution plan.

Common structures such as hero, cards, CTA, and footer are allowed only when their purpose is justified by the product logic and transformed into an original execution.

## Design Cognition Contract Handoff

After reference insight and before Template Orchestration, Codex must generate or internally complete the Design Cognition Receipt. Use `.design-brain/templates/DESIGN_COGNITION_RECEIPT.md` for human authoring and `.design-brain/templates/DESIGN_COGNITION_RECEIPT.json` for machine-readable gate validation.

Reference Insight feeds the 10 required cognition steps:

- Style DNA: the reference's type behavior, rhythm, density, color behavior, image direction, shape language, effects, and premium signal.
- Design Intent Lock: product type, medium, niche, target buyer, use case, marketplace value, and primary goal.
- Visual Grammar: grid, spacing cadence, hierarchy, color roles, surface depth, image treatment, effects, and component rhythm.
- Reference Boundary: what may be learned and what must not be copied.
- Color Role Re-Mapping: new palette identity from reference color roles, not copied hues.
- Visual Mood Reinterpretation: same emotional logic, new visual expression.
- Structural Reconfiguration: new hero grammar, section order, grid, CTA flow, and component layout.
- Pattern Divergence: divergence from the reference and prior batch templates.
- Section Logic: buyer journey role for every section, blocking generic Hero > Features > CTA defaults.
- Marketplace Readiness: concrete proof of depth, editability, preview value, source readiness, and commercial usefulness.

For website references, Style DNA extraction must explicitly include typography character, layout rhythm, color roles, image direction, density spacing, shape language, effect language, and premium visual signal. Visual Mood Reinterpretation must change composition, palette behavior, asset treatment, hierarchy, depth grammar, and visual emphasis. Structural Reconfiguration must produce a fresh hero grammar, grid system, section order, content rhythm, CTA placement, component layout, user reading flow, visual navigation, and desktop/tablet/mobile behavior plan.

If this handoff is missing, Template Orchestration, Design Simulation, and Post-Build Completion should treat the plan as incomplete.

## Section Layout Library Handoff

For website-template, Figma/source-template, marketplace, batch, anti-flat,
anti-generic, or layout-stiffness work, Reference Insight must hand off section
logic to `.design-brain/SECTION_LAYOUT_EXTRACTION_LIBRARY.md` before Template
Orchestration.

The handoff must identify:

- section roles that need catalog support
- product family and buyer decision point for each section
- density need for each selected section
- what the reference teaches about section purpose without copying execution
- which exact section treatment must not be copied
- whether a stable PASS catalog pattern exists or a new candidate must stay in
  `_incoming`

If the library is used in a build, the final layout fingerprint must include
`sectionPatternMix`, `sectionPatternIds`, `sectionDensityLimits`, and
`catalogDivergenceNotes`.

## Color And Palette Reconstruction Gate

Reference colors are evidence of role, mood, hierarchy, and buyer effect. They are not source tokens to copy.

When reading a reference, Codex must extract:

- what the background color is doing: calm, contrast, luxury, technical depth, warmth, editorial restraint, or utility
- what the accent color is doing: signal, CTA pressure, proof, urgency, trust, energy, softness, or category cue
- what surface colors are doing: separation, card depth, media readability, product focus, or premium restraint
- what contrast pattern is doing: making the offer feel bold, safe, serious, playful, clinical, high-end, or accessible

Codex must not copy the full palette, exact hex values, gradient sequence, glow color, or the same accent/CTA/background roles from the reference.

The output palette should be reconstructed from the new product type, target buyer, marketplace category, accessibility needs, and intended emotion. Codex may make a justified color assumption when the reference only gives mood evidence or when a different palette would better fit the new template product.

Before designing, Codex should be able to state: "The reference uses color to create X; this new template will reinterpret that function with Y palette and Z role mapping."

## Evidence Layer

Every designer-cognition claim must include:

- observed evidence from the reference
- inferred designer reason
- user or buyer effect
- business or product function
- reusable thinking logic
- originality transformation
- confidence level: high / medium / low

Do not make designer-cognition claims without visible evidence. If the evidence is weak, mark the confidence low and do not build a major template decision on that claim alone.

## Required Insight Extraction

Before designing from a reference, identify:

- Buyer decision model
- Reference purpose
- Design intent
- Audience
- Visual mood
- Color role logic
- Palette reconstruction plan
- Hierarchy logic
- Section logic
- Interaction or content flow
- Marketplace value
- Reusable lesson
- What must not be copied

## Abstract Logic Vs Execution Copy

Reuse abstract reasoning patterns, such as trust-before-pricing, calm-to-dense rhythm, evidence-before-action, visual proof, attention flow, buyer confidence, progressive disclosure, simplification after complexity, and enrichment where proof is needed.

Do not reuse recognizable execution patterns, such as exact composition, exact pacing, exact section treatment, exact component grouping, exact image placement, exact visual motif, exact CTA staging, or the same hero grammar plus the same mid-page rhythm plus the same conversion closure.

## Batch Usage

For multiple-template work, reference insight must happen per template cycle.

Do not extract one global set of reference lessons and apply it to every output. Use all relevant references as a Pattern Learning Pool to detect repeated designer thinking, then split the matched references into product-purpose groups of up to 10 varied references. Use one active group as the Execution Influence Pool for one specific output, and rotate to the next group for the next same-product build. For each template, infer buyer, purpose, audience, designer cognition, structure, visual logic, and do-not-copy boundary again before building that one template.

## Reinterpretation Rule

Preserve insight, not appearance.

Codex should intentionally change:

- Layout structure
- Section order when appropriate
- Color palette and color-role mapping
- Component grouping
- Composition and focal point
- Image placement and content rhythm
- Preview or cover framing
- Naming and product metaphor
- Hero grammar, CTA placement, responsive behavior, asset treatment, visual depth, and effect grammar for reference-led website templates

The final design must explain what was learned, what changed, how the structure was reinterpreted, why it is original, and why it fits the marketplace/product purpose.

## Continuous Learning Extension

Reference insight does not end when a design is built. A finished template is another piece of evidence.

For long-horizon learning, use this cycle:

1. Reference evidence
2. Designer cognition
3. Output or source-template audit
4. Weakest uncertainty or missed pattern
5. New learning question
6. Web evidence or category evidence
7. Answer distilled into designer schema
8. Next-build rule or Brain Design workflow update

The answer must improve future execution, not only explain the past. Useful schema should clarify buyer effect, section logic, visual rhythm, source-file editability, marketplace value, or originality boundaries. Keep this evidence separate from stable memory unless the user explicitly approves promotion.

## Safe Usage

Use `scripts/design_brain_reference_insight.py` to store reference lessons after visual inspection or user-provided description.

The script does not analyze images or URLs by itself. It stores human/Codex-described insights only.

Insights are not automatically stable design memory. They enrich the brain over time when recorded, reused, repeated, or later promoted through explicit controlled workflows.
