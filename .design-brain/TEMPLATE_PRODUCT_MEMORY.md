# Template Product Memory

This file stores stable rules for designing sellable template products. Use it together with `DESIGN_MEMORY.md`; it adds marketplace-specific judgment without replacing the core Design Brain workflow.

## Product Mindset

- A template product is not only a good-looking screen. It is a reusable asset that another buyer can edit, adapt, and ship.
- Design for a clear buyer and use case before choosing visuals.
- Marketplace-ready templates need a complete product story: cover, preview, section logic, responsive examples, editable components, and credible sample content.
- Yusuf's approved local corpus is documented in `.design-brain/APPROVED_TEMPLATE_CORPUS.md`. Use it as the local product-quality benchmark for approved page depth, design-system board style, preview packaging, and source-template expectations.
- The first impression should communicate the template category, niche, value, and quality within a few seconds.
- The product should feel intentionally art-directed, not assembled from generic blocks.
- Product packages should avoid stiff sameness across a seller catalog. A buyer should be able to tell templates apart by layout gesture and section silhouette, not only by palette, niche, or preview copy.

## Marketplace Readiness Rules

- Define the template type before designing: landing page, Figma website template, dashboard, SaaS template, UI kit, design system, branding kit, preview layout, cover layout, or overview layout.
- Define the target buyer: founder, designer, agency, SaaS team, creator, consultant, ecommerce owner, startup marketer, or internal product team.
- Match the visual mood to the buyer's business context and willingness to pay.
- Build reusable structure: named sections, consistent components, predictable spacing, editable text/image slots, and clear variants.
- Show enough breadth to prove value: hero, key sections, responsive states, component examples, and marketplace preview composition.
- Treat preview and cover layouts as part of the product, not an afterthought.

## Anti-Generic Rules

- Do not use random gradients, decorative blobs, or stock-like mockup framing unless they support the niche and product promise.
- Do not create a generic SaaS page with vague benefits, weak hierarchy, and interchangeable cards.
- Do not make every section the same card/grid rhythm.
- Do not make every template share the same centered vertical stack, split hero, proof strip, repeated card rows, FAQ, CTA, and footer rhythm.
- Do not hide the product behind overly abstract art direction.
- Do not overfit to one exact brand if the template must be reusable by many buyers.

## Editable Product Rules

- Use clear naming for sections, components, styles, tokens, and variants.
- Keep content replacement obvious: logos, headlines, screenshots, testimonials, pricing, metrics, images, and CTA text should be easy to swap.
- Preserve layout logic across desktop, tablet, and mobile.
- Include useful placeholder content that shows realistic structure without locking the buyer into a single company.
- Prefer modular sections that can be rearranged without breaking the design system.

## Preview Value Rules

- The cover should sell the outcome, not merely show a screenshot.
- The overview should show breadth: multiple screens, section breakdowns, components, responsive previews, and style details.
- Perspective mockups should improve clarity and desirability, not obscure the design.
- Section breakdowns should prove editability and completeness.
- The preview should make the buyer feel the product is complete, premium, and ready to adapt.

## Approved Package Standard

When scope allows, a premium approved Figma/template product should include:

- primary template page or website design
- design-system/foundations board
- marketplace main cover
- colors and typography preview
- features or section overview
- overview-template preview
- editable Figma source
- help/PDF/export support material when preparing for delivery

Do not treat a single attractive homepage as the whole product when the buyer expects a reusable marketplace package. If the current task intentionally asks for a smaller artifact, state the reduced scope instead of silently lowering the standard.
