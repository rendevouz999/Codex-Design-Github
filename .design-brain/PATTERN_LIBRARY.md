# Pattern Library

Store reusable UI and presentation patterns here. Add examples and lessons as the repository accumulates design work.

## Hero Sections

- Use one strong focal point and one clear primary action.
- Keep supporting copy short and specific.
- Make the brand, product, or offer visible in the first viewport.
- Use imagery or a real product preview when the subject benefits from visual inspection.

## Pricing Sections

- Make plan differences scannable.
- Emphasize the recommended plan through structure, not noisy decoration.
- Keep feature lists aligned and comparable.
- Ensure CTA hierarchy matches purchase intent.

## Dashboard Cards

- Prioritize scanability, density, and comparison.
- Use consistent padding, heading hierarchy, chart sizing, and status colors.
- Include empty, loading, error, and focus states when implemented in code.
- Avoid decorative card nesting.

## Landing Page Sections

- Build a clear rhythm: value, proof, details, conversion.
- Avoid overcrowded sections.
- Use section spacing to create momentum.
- Keep repeated components visually consistent.

## Preview Layouts

- Show the actual artifact clearly.
- Avoid tiny previews that cannot be inspected.
- Use a controlled background and enough contrast around the preview.
- Pair each preview with the most relevant metadata or action.
- Avoid decoration that competes with the artifact being previewed.

## Marketplace Presentation Layouts

- Lead with a polished overview mockup.
- Show multiple use cases or screen variants.
- Use consistent captions, spacing, and preview ratios.
- Make the template feel complete, editable, and ready to sell.
- Treat the presentation itself as a product-quality design surface.
- The approved local corpus often uses a marketplace cover with a title rail, browser crop of the real design, included-feature chips, and a bottom metadata strip. Reuse the sales logic, not the exact composition.

## Design Overview Layouts

- Present tokens, components, examples, and usage rules in a clear order.
- Show good and bad usage when useful.
- Keep documentation visual and scannable.
- Connect each rule to a practical implementation decision.

## Approved Website Template Rhythm

- Start with a product-specific hero promise, not a generic category headline.
- Move quickly into proof, selection, product discovery, or trust modules based on buyer friction.
- Alternate calm orientation sections with denser decision modules.
- Use category-specific blocks instead of universal 3-card grids.
- Add objection handling, pricing/package/form, FAQ, CTA, and footer closure when the purchase or booking path needs them.
- Use dark, colored, or textured rhythm breaks only when they create hierarchy, proof emphasis, or mood.

## Approved Design-System Board Pattern

- Show product-specific color roles, typography roles, spacing/radius/effect tokens, and practical primitives.
- Include auto-layout/source-template notes for Figma outputs.
- Include accessibility or contrast guardrails where the system needs them.
- Keep the board concise enough for a buyer to use; do not turn every unique editorial section into a component.

## Approved Preview Pack Pattern

- Treat cover, colors/typography, features overview, and overview-template as sellable design surfaces.
- Show the actual product clearly; avoid hiding it behind abstract mockups.
- Use preview copy to explain category, included value, editability, and source quality.
- Let preview color and layout inherit the template's visual language without becoming a duplicate of the page.
