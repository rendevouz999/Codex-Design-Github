# Presentation design workflow

This is the single presentation design owner for native and browser output. Brain Design still owns the general task lifecycle, cognition, originality and completion gates.

1. Determine buyer, use case, delivery mode, output, template kind and editable areas using `00_input_system/`. Separate speaker-led slides from reading-first documents before choosing density.
2. Study references using `PRESENTATION_DECK_INTELLIGENCE.md`: purpose, story, hierarchy, slide economy, rhythm, attention, grid, typography, color roles, effects, master/layout semantics, and edit resilience. Record the insight and recognizable details that must not be copied.
3. Plan story and slide-role matrix using `03_slide_archetypes/`. A serious reusable template needs at least ten distinct role layouts; a compact prototype, a narrow edit or a smaller explicitly requested product has its own scope. Never use that prototype as a shared page scaffold for unrelated final products.
4. Set coherent visual direction using `02_design_principles/`: color roles, type scale, spacing, grid, image treatment, visual emphasis, surface effects, data grammar and slide-to-slide rhythm. Ten ready theme references are in `../resources/themes/`; inspect the selected theme and adapt to the buyer rather than mixing all themes. Brand controls identity, Style controls communication method, Layout controls neutral structure, Deck combines identity/structure/application. Dashboard style and brand-specific guidelines are conditional references, never defaults.
5. For reusable templates load `native/template-designer.md`, `01_powerpoint_technical/` and the selected Create Template child. Author complete prototypes with explicit theme/master/layout/placeholder ownership. Source templates use meaningful text-clue image placeholders unless image generation was requested. For browser delivery, carry the same design decisions into the stage, navigation and motion contract; do not translate a PowerPoint canvas by blindly copying browser pixels.
6. Produce one selected artifact through the internal native or web workflow. Use existing runtime primitives before adding code. Respect source preservation, output collision checks and bounded subprocesses.
7. Review actual renders and contact sheets. Check hierarchy, thumbnail rhythm, variety, spacing, frame collisions, contrast, identity consistency, data clarity and placeholder resilience using `06_quality_control/` and `craft/`. Use the plugin's Design Critic general criteria as support; this sequence owns presentation review. Name concrete weaknesses, repair them, and inspect again. Do not infer visual PASS from OOXML or file existence.
8. Stress editable layouts with longer copy, more bullets, alternate image ratios, logo colors and changed chart values. Retain native text, shapes, charts and tables when promised. For source-preserving edits compare before/after style and unaffected slides. Reject or explicitly report unsupported fidelity rather than silently replacing native objects with screenshots.
9. Package outputs, contact-sheet/preview evidence, editable source, usage guide and receipts using `04_marketplace_standard/`. Apply triggered Brain completion gates. Report renderer, tested application and any unverified optional features.

Generic typography/color/composition utilities remain single-owned in the shared Brain craft layer. Their output enters this visual system; they do not create a second presentation workflow. Canvas/asset support is applied only to a concrete cover or image need. Core deck design does not require a remote image or Google Slides automation service.
